# NetCare 안정성·신뢰성 개선 보고서

작성일: 2026-11-23 (6시간 실측 반영 2026-11-24) · 대상: 장시간 메모리 증가, IP 스푸핑·TCP 주입 잔여 오탐, 커널 단계 패킷 누락 측정
작업 순서: 기존 코드 분석 → 원인 재현 → 수정 → 회귀 테스트 → 실측 검증

## 1. 문제별 원인 분석

### 1-1. 장시간 실행 메모리 증가

**분석 방법**
- 읽기 전용 메모리 진단 모듈 `netcare/diagnostics.py`와 API `GET /api/diag/memory`를 추가했다. 반환 항목은 RSS, tracemalloc 현재값·최대값, 엔진이 들고 있는 모든 컨테이너의 원소 수, 상위 할당 위치다.
- `scripts/perf_monitor.py --diag`가 이 값을 10초마다 JSONL로 기록한다.
- `scripts/memory_soak.py`(가속 소크)는 몇 시간 분량의 흐름 교체를 몇 분 안에 상태 보존 모듈에 넣는다. 초당 넣는 양은 TCP 3개, DNS 1쌍, QUIC 0.5개, 처음 보는 외부 주소 2개, 서버 연결 0.3개다.
- `scripts/session_churn.py`는 TCP 36,000개와 QUIC 9,000개 연결을 열고 닫은 뒤 15분 동안 정지시킨다. 정지 뒤 상태가 비워지는지 확인한다.

**Scapy `store` 설정 확인**: 기존 코드도 `AsyncSniffer(..., store=False)`라서 스니퍼가 패킷 목록을 쌓지는 않았다. 하지만 아래 ⑤번처럼 **처리 큐 자체가 Scapy 객체를 들고 있는** 문제가 있었다.

**찾은 원인**

| # | 원인 | 근거 | 영향 |
|---|---|---|---|
| ① | `LiveStats`의 출발지·목적지·포트별 누적 카운터에 상한이 없음 | 가속 6시간: 출발지 키 125,279개, 목적지 82,080개로 직선 증가 (stats.py:73 할당 9.9MB) | 장시간 직선 증가 |
| ② | `AdvancedDetector.target_ok`, `syn_count`, `in_synack_for_server`에 시간 만료가 없음 | 가속 6시간: target_ok 75,589개로 직선 증가. syn_count는 out_syn이 2만을 넘을 때만 정리됨 | 장시간 직선 증가 |
| ③ | `dns_q`·`ttl_hist`는 상한(2만)에 닿으면 새 항목을 받지 않음 (지우지도 않음) | 가속 1시간에 ttl_hist가 20,000에 닿은 뒤 새 출발지 학습 중단. dns_q는 응답 뒤에도 남음 | **기능 버그**: 장시간 뒤 DNS 위조 탐지·RTT 측정·TTL 비교가 조용히 멈춤 |
| ④ | 트래픽이 멈춰 평가 창이 비면 `Detector.evaluate`가 하위 탐지기 정리 전에 반환 | 세션 반복 시험: 정지 15분 뒤에도 target_ok 36,000, open_ports 36,000, out_syn 17,180, integ.flows 8,551이 그대로 | 유휴 중 메모리를 놓지 않음 |
| ⑤ | 처리 큐가 **해석된 Scapy 객체**를 최대 50,000개 보관 | 실측(수정 전 서버): 고속 유입 때 큐 50,000개가 차며 RSS 1,272MB. 유입이 끝나 큐가 빈 뒤에도 RSS 1,074MB (tracemalloc 기준 Python 객체는 108MB) | 고속 유입 한 번으로 RSS가 수백 MB 늘고 돌아오지 않음 (할당자 단편화) |
| ⑥ | 무결성 탐지 UDP 순서 번호 흐름(`udp_seen`)에 만료가 없음. 상한에 닿으면 새 흐름 검사 중단 | 코드 분석 | 기능 버그 (장시간 뒤 재전송 탐지 중단) |
| ⑦ | CrowdSec 호환 통·열린 포트 기록이 개수 상한(2만·5만)에 닿을 때만 정리됨 | 가속 6시간: compat.open_ports 26,629, 통 10,824로 증가 | 상한까지 증가 |

이미 상한이 있어 문제가 없던 것: TCP 재조립(4,096 흐름 · 조각 2,048), QUIC(4,096 연결), 암호화 흐름 표시(LRU 50,000), IP 이름표(20,000), 최근 이벤트(300), 초 단위 그래프(1시간).

### 1-2. 잔여 오탐

이전 실측 DB에 저장된 원시 패킷으로 원인을 직접 확인했다.

**(가) TCP 주입 오탐 — 로드밸런서 RST** (34.149.66.165:443, 1시간 실측에서 5건, 수정 전 6시간 실측 진행 중에도 발생)

```
IN  ttl=116 PA  seq=17263533 len=24
IN  ttl=116 FA  seq=17263557            ← 서버가 먼저 연결 종료(FIN)
OUT ttl=64  PA  seq=2504574747 len=24   ← 늦게 보낸 내 데이터
OUT ttl=64  FA
IN  ttl=108 R   seq=17263558 ack=0 id=0 ← 정확히 예상한 SEQ(FIN+1), TTL만 다름 (로드밸런서가 대신 응답)
IN  ttl=108 R   seq=17263558 ack=0 id=0
```

원인: 기존 규칙은 **연결 평소 TTL과 5홉 이상 다른 RST**를 SEQ와 관계없이 주입 징후로 셌다. 이 RST는 SEQ가 정확하고, 상대가 이미 FIN을 보낸 뒤의 정상 종료다.

**(나) IP 스푸핑 오탐 — Google Cloud TTL** (34.104.35.123)

| 연결(내 포트) | 53641 | 49329 | 54254 | 53794 | 49182 | 56357 | 54953 | 55148 | 55578 |
|---|---|---|---|---|---|---|---|---|---|
| TTL | 117 | 117 | 117 | 117 | 54 | 54 | 54 | 117 | 54 |

원인: 같은 주소가 **연결마다** 다른 TTL을 쓴다(백엔드·경로가 다름). **연결 안에서는 항상 일정**하다. 기존 규칙은 출발지·프로토콜별 TTL 분포 하나로 비교했다. 그래서 TTL 54인 연결의 패킷이 13건씩 '위조 징후'가 됐고, TTL 하나만으로 알림이 났다.

### 1-3. 커널 단계 패킷 누락

- 기존 코드는 응용 단계(큐가 가득 차 버린 패킷)만 셌다.
- Scapy `AsyncSniffer(iface=…)`는 내부에서 소켓을 만들고 감추기 때문에, 커널 캡처 소켓 통계를 읽을 방법이 없었다.

조사한 OS별 제공 범위:

| 단계 | macOS | Linux | Windows |
|---|---|---|---|
| 커널 캡처 소켓 | BPF `BIOCGSTATS`: `bs_recv`(필터 적용 전 BPF가 본 패킷), `bs_drop`(BPF 버퍼가 가득 차 버림) | AF_PACKET `PACKET_STATISTICS`: `tp_packets`, `tp_drops` (읽을 때마다 0으로 초기화 → 누적) | Npcap `pcap_stats`: `ps_recv`, `ps_drop`, `ps_ifdrop` |
| NIC | `ifi_iqdrops`·`ierrors` (psutil). **링 버퍼 하드웨어 누락은 제공하지 않음 → 측정 불가** | `rx_dropped`·`rx_missed_errors`·`rx_fifo_errors` (/sys) | `InDiscards`·`InErrors` |
| 실제 확인 | **실측 확인** (en5, en0, lo0) | **실측 확인** (GitHub Actions Ubuntu, lo·eth0 — 5-3) | **미검증** (가짜 소켓 단위 테스트만, CI에 Npcap 설치 불가) |
