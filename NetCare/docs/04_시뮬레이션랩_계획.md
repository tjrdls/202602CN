## 1. 현재 구조 분석

### 1-1. 데이터 흐름 (현재)
```
[입력 3종]                         [단일 Engine 인스턴스]                         [저장: data/netcare.db]
실시간 캡처(Scapy AsyncSniffer) ┐
pcap 파일(PcapReader)           ├─▶ 큐 ─▶ parse_packet ─▶ LiveStats ─┐        packets / traffic_minute
테스트 시나리오(synthetic.py)    ┘                       └▶ Detector ─┴▶ Explainer ─▶ anomalies (source 컬럼)
                                                                         ActionManager ─▶ actions
```

### 1-2. 이번 요청과 관련된 현재 상태
| 항목 | 현재 | 이번 요청과의 차이 |
|---|---|---|
| 테스트 데이터 | `testdata/synthetic.py`의 시나리오 5종(정상, SYN Flood, 포트 스캔, DNS 장애, 트래픽 급증)을 실시간 속도로 재생, `source='test'` | 12종으로 확장 필요. 시나리오 조건(강도·시드) 설정, 정답 라벨, 실험 기록이 없음 |
| 데이터 분리 | 같은 DB에 `source` 컬럼(live/pcap/test)으로 구분, 리포트는 기본으로 live만 집계 | "엄격한 분리" 요구 → **DB 파일 자체를 분리**하는 편이 안전함 |
| 탐지 규칙 | 9종 (과다 패킷, SYN, 포트 집중, 급증, 반복 연결, 스캔, 과다 통신, DNS 실패, ping 기반 연결 품질) | **IP·ARP·DNS 스푸핑, 패킷 손실·지연·지터·대역폭 제한·연결 중단을 패킷만으로 판단하는 규칙이 없음** (현재 손실·지연은 실제 ping 측정으로만 판단) |
| 대응 조치 | 테스트 출처 징후 → 명령 미리보기만 하는 시뮬레이션 | "조치 전후 비교"가 불가능함. 조치가 가상 네트워크에 실제 효과를 내도록 해야 함 |
| 평가 지표 | 없음 | 탐지 소요 시간, 오탐, Precision/Recall/F1/FPR 필요 |
| 재현성 | 시나리오 시드는 고정, 하지만 실시간 재생 시각에 의존 | 이미 "처리한 패킷 시각 기준 평가"로 바꿔 두어서, 같은 시드·조건이면 같은 결과가 나오게 만들 수 있음 |

## 2. 구현 가능성과 기술적 한계

### 2-1. 실행 환경
| 단계 | 방식 | 이 Mac에서 가능? |
|---|---|---|
| A | **Scapy로 가상 패킷·PCAP 생성** → NetCare 파이프라인에 직접 주입 (네트워크로 전송하지 않음) | ✅ 가능, 모든 OS |
| B | **Linux 네트워크 네임스페이스**: 가상 클라이언트·서버·DNS·공격자 + 외부 연결 없는 브리지, `tc netem`으로 장애 주입 | ❌ macOS에는 네임스페이스와 `tc`가 없음 → **Linux(VM) 필요** |

이 Mac의 UTM에 **`Ubuntu-SP` VM이 실행 중**인 것을 확인했습니다. B단계를 실제로 검증하려면 이 VM 안에서 NetCare와 실험실을 돌려야 합니다(아래 질문 참고).

### 2-2. 시뮬레이션별 가능성

| 유형 | A단계 (Scapy 생성) | B단계 (netns 실시간) | 탐지 방법(신규 규칙 포함) | 탐지 난이도/한계 |
|---|---|---|---|---|
| IP Spoofing | ✅ | ✅ 공격자 ns에서 위조 출발지로 전송 | ① 같은 IP의 TTL(홉 수) 급변 ② 외부에서 들어온 패킷의 출발지가 내 IP·사설/예약 대역 ③ 요청한 적 없는 SYN-ACK/RST 수신(백스캐터) ④ LAN IP인데 학습된 MAC과 다름 | **중간.** TTL까지 맞춘 정교한 위조는 수동 분석으로 구분할 수 없음 |
| ARP Spoofing | ✅ | ✅ | IP→MAC 매핑 변경, 게이트웨이 IP를 주장하는 MAC이 2개 이상, 요청 없는 ARP 응답 반복 | **쉬움.** 실제 DHCP 재할당이나 장비 교체 때 오탐 가능 → 학습 기간과 화이트리스트로 완화 |
| DNS Spoofing | ✅ | ✅ 가상 DNS가 조작된 응답 | 같은 질의 ID에 서로 다른 답이 2개(경합 위조), 질의하지 않은 서버의 응답, 이미 학습한 도메인→IP가 급변 | **중간.** 처음부터 위조된 응답 하나만 오면 구분할 수 없음(DNSSEC 없이는 원리적 한계) |
| Port Scanning | ✅ (기존) | ✅ | 기존 규칙 + **수신 UDP 스캔 집계 보완** | 쉬움. 느린 스캔은 긴 윈도우 추가로 일부 보완 |
| SYN Flood | ✅ (기존) | ✅ | 기존(핸드셰이크 완료율, 분산 SYN) | 쉬움 |
| 반복 연결 | ✅ (기존) | ✅ | 기존 + **로그인 서비스 포트 무차별 대입 규칙 보완** | 쉬움 |
| Packet Loss | ✅ (재전송 모델링) | ✅ `netem loss` | **TCP 재전송 비율**(같은 SEQ 재송신), 중복 ACK | 중간 |
| Latency | ✅ | ✅ `netem delay` | **SYN→SYN-ACK 왕복 시간, DNS 응답 시간** 중앙값이 기준 초과 | 쉬움 |
| Jitter | ✅ | ✅ `netem delay X Y` | 위 RTT의 변동(표준편차/연속 차이 평균, RFC 3550 방식) | 중간 |
| DNS Failure | ✅ (기존) | ✅ 가상 DNS 중지/SERVFAIL | 기존 규칙 | 쉬움 |
| Bandwidth Limiting | ✅ | ✅ `tc tbf` | 흐름 처리량이 일정 값에 막혀 평평해지면서 RTT 증가(큐 적체) | **어려움.** 수동 관찰만으로는 "원래 느린 회선"과 구분이 거의 불가능 → "의심" 수준으로만 표시하고, 미탐이 많을 수 있다고 명시 |
| Connection Failure | ✅ | ✅ 서버 ns에서 서비스 중지/iptables DROP | 이전에 응답하던 서버로의 SYN이 무응답(타임아웃) 또는 RST | 쉬움 |

### 2-3. 정직하게 밝혀야 할 한계
1. **자기 평가 편향:** A단계는 생성기와 탐지기를 같은 팀이 설계하므로, Precision/Recall이 실제보다 좋게 나옵니다. 완화책은 ① 강도를 단계별로 바꿔 보는 실험(기준 아래 강도에서는 "놓치는 것이 정상"임을 보여 줌) ② 시드를 바꾼 반복 실행 ③ 정상 배경 트래픽 섞기 ④ B단계 실측과의 비교입니다. 보고서에는 "합성 데이터 기준 지표"라고 반드시 표기합니다.
2. A단계 패킷은 **모델**입니다. TCP 혼잡 제어 같은 실제 동작은 B단계에서만 재현됩니다.
3. 새 규칙(ARP/IP/DNS 스푸핑, RTT 기반 지연·지터 등)은 실시간 캡처에도 적용됩니다. 그래서 **실제 네트워크 오탐 재검증**이 필요합니다(지난번처럼 실측으로 확인).
4. B단계 실험실 안의 방화벽 조치는 **가상 서버 네임스페이스의 iptables**에만 적용됩니다. 진짜 규칙 변경이지만 호스트와 실제 네트워크에는 영향이 없고, 지난번 "Linux iptables 백엔드 미검증" 항목을 검증하는 기회가 됩니다. macOS pf 미검증 상태는 그대로 남습니다.

## 3. 설계

### 3-1. 엄격한 데이터 분리
- 실험실은 **별도 Engine 인스턴스 + 별도 DB 파일(`data/simlab.db`)**을 씁니다. 기존 홈/패킷/문제 해결/리포트는 실험 데이터를 **구조적으로 볼 수 없습니다**(같은 탐지 코드를 쓰되 저장소가 다름).
- 실험실 Engine의 ActionManager는 **실제 방화벽 백엔드를 아예 갖지 않습니다**. A단계에서는 가상 방화벽만, B단계에서는 실험실 네임스페이스 iptables만 씁니다(호스트 명령 실행 경로 자체가 없음).
- 모든 실험 레코드에 `source='sim'`, `experiment_id`, `stage(A/B)`를 붙이고 UI에는 "시뮬레이션" 배지를 항상 표시합니다.
- 기존 "테스트 데이터" 5종(캡처 모달)은 지우지 않고 그대로 둡니다(기존 기능 유지).

### 3-2. 시나리오 정의 (선언형)
```python
Scenario(id="arp_spoof", kind="attack", title="ARP Spoofing",
         params={"intensity": 1.0, "duration": 30, "attack_start": 10, "attack_end": 25, "seed": 7, "background": "normal"},
         expected={"arp_spoof"},            # 정답 라벨: 이 기간에 나와야 하는 탐지 유형
         acceptable={"ip_spoof"},           # 관련 징후 (오탐으로 세지 않음)
         remediation=["static_arp", "block_mac"])  # 가상 조치와 효과 모델
```
- 패킷마다 정답 라벨(benign / 공격 유형)을 메타데이터로 보관합니다(헤더에는 넣지 않음).
- 같은 시드와 조건이면 바이트 단위로 같은 PCAP이 나옵니다. 실험 PCAP은 `data/simlab/pcap/`에 저장하고 다운로드할 수 있게 합니다.

### 3-3. 실험 평가
- **탐지 여부/소요 시간:** 공격 시작부터 기대 유형이 처음 탐지될 때까지(패킷 시각 기준).
- **1초 창 단위 혼동 행렬:** 정답(공격 진행 중인 창)과 예측(해당 유형 탐지가 활성인 창)을 비교합니다.
  - TP: 공격 창 + 기대 유형 탐지 / FN: 공격 창 + 미탐 / FP: 정상 창 또는 기대·관련 외 유형 탐지 / TN: 정상 창 + 탐지 없음
  - Precision, Recall, F1, FPR = FP/(FP+TN). 실험별, 유형별, 전체로 계산합니다.
- **강도 단계 실험(sweep):** 강도 0.25×~3×와 시드 N개를 반복해 "강도별 탐지율" 곡선을 그립니다.
- 저장 항목: 유형, 조건(JSON), 생성 패킷 수, 탐지 여부, 소요 시간, 오탐 수, 탐지 근거, 진단 결과, 조치와 성공 여부, 조치 전후 지표.

### 3-4. 조치 전후 비교 (가상 효과 모델)
| 조치 | A단계 효과 | B단계 효과 |
|---|---|---|
| IP 차단 | 생성기가 이후 해당 출발지 패킷을 "가상 방화벽에서 버림" 처리 | 서버 ns에 `iptables -I INPUT -s IP -j DROP` (롤백 `-D`) |
| 정적 ARP / 의심 MAC 차단 | 위조 ARP 무시 | 클라이언트 ns에서 `ip neigh replace … nud permanent` |
| DNS 캐시 초기화 / 신뢰 DNS로 전환 | 위조 응답 중단 | 가상 DNS 재시작 |
| 장애 해제(진단용) | 장애 주입 종료 | `tc qdisc del` |
- 비교 지표: 조치 전후 10초의 공격 패킷 수, 핸드셰이크 완료율, RTT, 손실률, 징후 지속 여부.
- 효과 모델은 "이 조치가 성공했을 때의 결과"를 재현하는 것이지 실제 효과를 증명하는 것이 아니라는 점을 화면과 문서에 표시합니다(A단계). B단계는 실제 측정입니다.

### 3-5. B단계 네임스페이스 토폴로지 (Linux)
```
          br-netcare (10.77.0.0/24, 외부 인터페이스 없음, NAT·기본 경로 없음)
     ┌──────────┬──────────┬──────────┬──────────┐
  ns client   ns server   ns dns     ns attacker     ← NetCare는 br-netcare를 캡처
  10.77.0.10  10.77.0.20  10.77.0.53  10.77.0.66
  (curl/dig)  (http/ssh)  (가상 DNS)   (Scapy 공격)
  장애 주입: 해당 veth에 tc netem / tbf
```
**격리 안전장치(스크립트가 시작 전 검사, 실패 시 중단):** 브리지에 물리 NIC가 없을 것, 각 ns에 기본 경로가 없을 것, 공격 도구는 목적지가 10.77.0.0/24가 아니거나 인터페이스가 실험실 ns 밖이면 전송 거부, 종료 시 ns·브리지·qdisc 정리(teardown), 실행 전 root 확인과 안내.

### 3-6. UI
- 상단 메뉴에 **"실험실"** 탭을 추가합니다(기존 4개 탭 유지).
- 공격 6종과 장애 6종을 카드로 보여 줍니다(아이콘, 설명, 지원 단계 A/B, 최근 결과 배지).
- 카드 선택 → 조건 설정(강도, 기간, 시드, 배경 트래픽, 실행 속도: 즉시/실시간) → 실행
- 실행 중: 실시간 그래프(PPS, 공격 구간 음영, 탐지 시점 표시), 탐지 이력 타임라인
- 결과: 탐지 여부·소요 시간·근거·진단, 조치 실행과 전후 비교 차트, 지표 카드(P/R/F1/FPR), 실험 이력 표, CSV/PCAP 내보내기
- 기존 디자인 시스템(카드, 색, 배지)을 그대로 씁니다. "시뮬레이션" 배지는 보라색으로 표시합니다.

## 4. 단계별 개발 계획

| 단계 | 내용 | 산출물 | 검증 |
|---|---|---|---|
| **S1** | 실험실 기반: 별도 Engine·DB, 시나리오 프레임워크, 정답 라벨, PCAP 저장, 기존 5종 이식 | `netcare/simlab/` | 같은 시드 → 같은 PCAP·같은 결과(재현성 테스트), 메인 DB에 0행 기록(분리 테스트) |
| **S2** | 시나리오 12종 생성기 + **신규 탐지 규칙**(IP/ARP/DNS 스푸핑, 재전송 손실, RTT 지연·지터, 대역폭 제한 의심, 연결 중단, 수신 UDP 스캔, 로그인 무차별 대입) | detector 확장 | 규칙별 단위 테스트, **실제 네트워크 오탐 재검증** |
| **S3** | 평가: 혼동 행렬, P/R/F1/FPR, 탐지 소요 시간, 강도 sweep·반복 실행, 실험 이력 저장 | `simlab/evaluate.py` | 손으로 계산한 작은 사례와 일치하는지 확인 |
| **S4** | 가상 대응 조치와 전후 비교 | 가상 방화벽/ARP/DNS 효과 모델 | 조치 후 공격 패킷 감소 확인 |
| **S5** | UI "실험실" 탭 | 카드·조건·실시간 그래프·이력·지표 | UI E2E 확장 |
| **S6** | B단계: netns 구성/정리 스크립트, 가상 서비스, 장애·공격 에이전트, NetCare 연동 | `scripts/netns_lab.sh`, `simlab/netns/` | **Linux VM에서 실측** (가능할 경우) |
| **S7** | 통합 테스트, 문서·발표 자료 갱신 | docs 갱신 | 전체 pytest + E2E |

S1~S5는 이 Mac에서 끝까지 구현하고 검증할 수 있습니다. S6은 Linux 환경이 있어야 검증할 수 있습니다.
