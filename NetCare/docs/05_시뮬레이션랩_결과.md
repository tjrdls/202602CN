### S2. 시나리오 12종 + 탐지 규칙
**신규 규칙 8종** (`detection/advanced.py`, 기존 Detector에 포함): ARP 스푸핑 의심, IP 스푸핑 의심, DNS 위조 의심, 지연 증가, 지터, 데이터 손실(재전송·3중 중복 ACK·ping 무응답), 연결 중단, 대역폭 제한 의심. 여기에 기존 규칙 보완 1건(들어오는 UDP 스캔 집계)을 더했습니다.

**과장 방지 (사용자 요청 반영)**
- IP 스푸핑, DNS 위조: 확실성 '의심(suspected)', 위험 수준은 **최대 '주의'**, 제목에 "의심"
- 대역폭 제한: '의심' + '정보' 등급
- ARP 스푸핑: '가능성 높음(likely)'이지만 제목은 "의심". 게이트웨이를 사칭할 때만 '위험'

**발견하고 수정한 버그 (S2)**
| # | 발견 경위 | 원인 | 수정 |
|---|---|---|---|
| 1 | 기존 회귀 테스트(정상 시나리오) 실패 | 내 MAC을 모를 때 모든 프레임을 "외부 장치"로 보고 내 IP를 위조로 판정 | MAC 기반 판단은 내 MAC을 알 때만 수행 |
| 2 | 오프라인 점검 | 연결 중단 탐지가 10초 늦음(10초 창 안의 이전 성공 응답 때문) | "마지막 성공 이후 연속 실패 횟수" 방식 → 탐지 2초 |
| 3 | **실제 네트워크 재검증** | 서브넷 밖 `192.168.1.1`을 여러 장비가 주장 → ARP 스푸핑 오탐 | 내 서브넷(예: 172.16.104.0/22) 안의 주소만 판단 |
| 4 | **실제 네트워크 재검증** | 위와 같은 IP의 MAC 불일치 → IP 스푸핑 오탐 | MAC이 여럿인 IP는 불일치 판단 제외 |
| 5 | **실제 네트워크 재검증** | **기존 DNS 실패 규칙의 잠재 버그**: mDNS(224.0.0.251) 질의를 무응답으로 셈 | mDNS, LLMNR, 멀티캐스트 DNS를 무응답 판정에서 제외 |
| 6 | 벤치마크 | 지연이 300ms→13ms로 바뀌는 순간(계단)을 지터로 오인(FP 5초) | 연속 RTT 차이의 **중앙값** 사용 |
| 7 | 벤치마크 | 평소 스트리밍이 우연히 평평할 때 지연 장애와 겹쳐 "대역폭 제한 의심" | 평탄도 기준 0.15 → 0.10 |

**실제 네트워크 오탐 재검증 (en5, 수정 후)**: 평상시 150초 동안 웹 요청 80회와 DNS 조회 → 오탐 **0건**. 이어진 약 92MB 다운로드 구간에서는 기존에 문서화된 사용량 신호만 나왔습니다(과다 패킷 주의/정보, 사용량 급증 주의, 포트 집중 정보, 과다 통신 정보).

### S3. 평가 (P/R/F1/FPR, 탐지 소요 시간, 반복·강도 단계)
- 1초 단위 혼동 행렬을 씁니다. 공격 구간은 (시작, 종료]이고, 종료 후 W초는 유예 구간입니다(탐지 창에 남은 데이터 고려). '관련 징후'는 TP도 FP도 아닙니다.
- 손으로 계산한 사례와 일치하는지 단위 테스트로 확인했습니다.
- 저장 항목: 유형, 조건, 생성 패킷 수(공격 패킷 수), 탐지 여부, 소요 시간, 오탐 목록, 탐지 근거, 진단 결과, 조치·성공 여부·전후 지표, 1초 타임라인, PCAP.

### S4. 가상 조치와 전후 비교
| 시나리오 | 가상 조치 | 비교 지표 | 결과 (예) |
|---|---|---|---|
| SYN Flood / 포트 스캔 / 반복 연결 | 내 컴퓨터 방화벽(가상) | 공격자에게 보낸 응답/초 | SYN Flood 10.0 → 0 |
| ARP Spoofing | 정적 ARP(가상) | 공격자 MAC으로 간 내 프레임/초 | 25.5 → 0 |
| DNS Spoofing / DNS Failure | 암호화 DNS 전환(가상) | 위조 응답 / 실패 조회 | 2.0 → 0 |
| IP Spoofing | 공유기 인그레스 필터링(가상) | LAN에 들어온 위조 패킷/초 | - |
| 지연·지터·손실·대역폭·연결 중단 | 진단 + **장애 주입 종료(실험 제어)** | RTT·손실 등 | 지연 98.6ms → 7.0ms |

- 가상 방화벽은 "캡처가 방화벽보다 먼저 일어나는" 실제 원리를 따릅니다. 그래서 들어오는 공격 패킷은 계속 캡처되고 탐지도 계속되며, **응답만** 멈춥니다. 화면에도 그렇게 설명합니다.
- 장애 해제는 NetCare의 해결 기능이 아니라 실험 제어라고 명시했습니다.
- 가상 효과 모델은 "조치가 성공했을 때의 결과"를 재현할 뿐 실제 효과를 증명하지 않는다는 문구를 결과에 표시합니다.

### 전체 156회 (낮은 강도 포함): Precision 100%, Recall 66.4%, F1 79.8%, FPR 0%
**강도별 탐지율:** 스푸핑 3종·포트 스캔·SYN Flood·연결 중단은 0.25×에서도 100%입니다. 반복 연결은 0.25×에서 0%입니다(기준 아래, 의도된 미탐). 손실·지연·지터·대역폭은 0.5× 이하에서 0%이고, DNS 실패는 0.5×에서 67%입니다. 전체 Recall이 낮은 이유는 대부분 **기준 아래 강도를 일부러 넣었기 때문**입니다.

### 결과 해석 (과장 금지)
- FPR 0%와 Precision 100%는 **이 합성 배경 트래픽 기준**입니다. 실제 네트워크에서는 2-3과 S2의 실측처럼 다운로드 같은 상황에서 사용량 신호가 나오고, 실측 과정에서 오탐 3건을 찾아 고쳤습니다.
- 스푸핑 3종의 소요 시간이 1~2초로 짧은 이유는 합성 공격이 위조 징후를 매초 여러 번 만들기 때문입니다. 실제 공격은 더 드물고 은밀할 수 있습니다.
- Recall이 100%가 아닌 주된 이유는 탐지 창(10초)에 따른 구조적 지연입니다. 공격 시작 직후 몇 초는 FN으로 셉니다.
- 장애 계열(손실·지연·지터·대역폭)은 강도 1× 이상에서만 탐지됩니다. 약한 품질 저하는 놓칩니다.
- 6번 수정(지터 중앙값)으로 오탐은 사라졌지만, 지터 Recall이 75% → 62%로, 평균 소요가 6.0 → 8.7초로 나빠졌습니다(트레이드오프).

## 남은 한계
1. 합성 데이터 자기 평가 편향 (위 해석 참고). 이를 보완하려면 S6(실제 TCP 스택과 tc netem)이 필요합니다.
2. 패킷만으로 판단하는 원리적 한계: TTL까지 맞춘 IP 위조, 처음부터 위조된 DNS 응답 하나, 원래 느린 회선(대역폭)은 구분할 수 없습니다.
3. 반복 연결 규칙은 연결이 성공하는 로그인 무차별 대입(SSH 등)을 잡지 못합니다(이전 보고와 같음).
4. 실험실 시나리오에서 "관련 징후"가 함께 나옵니다(예: DNS 위조 시 IP 스푸핑 의심, 대역폭 제한 시 지연 증가). 평가에서는 TP도 FP도 아닌 것으로 처리합니다.
5. 실험실 엔진은 메인 설정의 탐지 임계값을 공유합니다(같은 엔진 검증 목적). 설정을 바꾸면 이후 실험 결과도 달라집니다.
6. 다운로드 같은 대용량 정상 트래픽에서 '주의' 등급 사용량 신호가 나오는 동작은 그대로입니다(이전 보고에 문서화).
7. macOS pf 실제 차단은 여전히 미검증입니다. S6에서는 VM 안 네임스페이스의 iptables로 Linux 백엔드를 검증할 수 있습니다.
