### pytest 주요 항목
- **파서:** TCP 필드·방향·서비스, DNS 질의/응답/NXDOMAIN, ICMP, IPv6, TLS ClientHello SNI 추출, 암호화 데이터의 미리보기 비표시, 계층 트리 한국어 라벨, 손상 패킷에서도 예외 없음
- **탐지:** 정상 시나리오에서 경고 0건, SYN Flood(핸드셰이크 미완료) 위험 등급, 포트 스캔, DNS 장애(오류+무응답), 트래픽 급증 오탐 완화(양방향 다운로드 → 위험 아님, 443 집중 → 정보), 화이트리스트, 임계값 설정 반영, EWMA z-score, A/AAAA 부분 응답 비탐지, 성공하는 반복 연결 비탐지
- **API:** Host 검사·커스텀 헤더(403), 잘못된 인터페이스, pcap 가져오기 → 포트 스캔 탐지와 통계가 처리 패킷 수와 정확히 일치, 비 pcap 업로드 거부, 동의 없는 차단 거부, 보호 IP 차단 거부, 잘못된 IP·알 수 없는 조치 거부, 안전 조치 실행, 설정 검증, 동의 없는 자동 차단 활성화 거부, "정상이에요" 클릭 시 화이트리스트 추가, 리포트 기본 집계에서 테스트·파일 데이터 제외, CSV 5종과 PDF 생성
- **조치/점수:** 보호 IP 판별, 명령 주입 문자열 거부, 3개 OS 방화벽 스크립트가 NetCare 전용 규칙만 다루는지, pf 출력 파싱과 롤백 토큰, 점수 감점 규칙, ping 출력 파싱(macOS/Windows), 설정 검증 실패 시 이전 값 유지

### UI E2E 점검 항목 (실제 버튼 클릭)
홈 로드·점수 → 캡처 모달(인터페이스 목록) → 테스트 데이터 재생·배지 → KPI 반영 → 문제 해결 상세·게이지 → 차단 모달(동의 전 실행 버튼 비활성, 부작용·시뮬레이션 안내) → 동의 후 실행 → 결과 표시 → 되돌리기 → 안전 조치(동의 없이 실행 가능) → 정상 처리 모달 → 패킷 목록·상세 드로어 → DNS 필터 → 전문가 모드 → 설정(자동 차단 경고, 동의 없이 저장 거부, 기본값 유지) → 리포트 그래프·이력 → CSV 5종 → 모바일 하단 탭 → JS 오류 없음

## 2. 실제 네트워크 실험

### 2-1. 실시간 캡처 (en5, USB 유선 LAN)
| 확인 항목 | 결과 |
|---|---|
| 캡처 시작·중지 | 정상. 잘못된 필터(`tcp prt 443`)는 시작 전에 문법 오류로 안내 |
| 프로토콜 | TCP, UDP, ICMP, ARP, IGMP, IPv6 모두 수집 |
| HTTPS | ClientHello에서 SNI(`www.naver.com`, `www.google.com` 등)를 평문으로 표시. 본문은 "암호화되어 볼 수 없음"으로 표시 |
| DNS | 질의·응답 해석, 응답으로 IP→도메인 매핑을 학습해 목록에 도메인으로 표시 |
| ping | 요청/응답 해석 |
| 처리 성능 | 약 100MB 다운로드 중 초당 약 6,700개 패킷, 버린 패킷 0 (처리 지연은 발생, 아래 3-4 참고) |

### 2-2. 루프백 실험 (`scripts/traffic_lab.py`, lo0 캡처, 127.0.0.1 전용)
| 실험 | 실제 생성 트래픽 | 탐지 결과 |
|---|---|---|
| normal | 정상 TCP 연결 40개(핸드셰이크 완료) | **탐지 없음** (수정 후, 3-2 참고) |
| scan | 닫힌 포트 150개에 연결 → RST 150개 | 포트 스캔 **위험**(150곳/기준 40), SYN 급증 **주의**(완료율 0%) |
| repeat | 같은 닫힌 포트에 80회 → RST 80개 | 반복 연결 **주의**(80/30, 완료율 0%), SYN 급증 **주의** |
| udp | 8초 동안 UDP 6,400개 | 포트 집중 **위험**(98.8%, 일반 서비스 아님), 과다 패킷 **정보** |
| bulk | 로컬 TCP로 200MB(200Mbps) | 트래픽 급증(학습 전 고정 기준), 과다 패킷(양방향 → 등급 낮춤), 포트 집중 |

참고: 루프백에서는 출발지와 목적지가 같은 127.0.0.1이라 "양방향" 판정이 항상 참이 됩니다. 루프백 실험의 등급은 참고용입니다.

### 2-3. 실제 다운로드로 통계 탐지와 오탐 완화 확인 (en5)
1. 캡처를 시작하고 66초 동안 평소 사용량을 학습했습니다. 기준선: 평균 14KB/s, 표준편차 4.4KB/s.
2. **평상시 66초 동안 탐지: 0건** (실제 네트워크에서 오탐 없음)
3. 공개 속도 테스트 파일 약 89MB를 15초 동안 내려받았습니다(약 5.9MB/s).

| 탐지 | 등급 | 근거 |
|---|---|---|
| 트래픽 급증 | 주의 | **EWMA z-score 7.51** (기준 4), 학습 70초 |
| 다운로드 서버의 과다 패킷 | 주의 (위험에서 한 단계 낮춤) | 역방향 ACK 비율 0.19 → 양방향 통신으로 판정 |
| 내 컴퓨터의 과다 패킷(ACK) | 정보 | 내 컴퓨터의 양방향 전송 |
| 특정 IP 과다 통신 | 정보 | 98.7% 점유, 양방향 |
| HTTPS 포트 집중 | 정보 | 일반 서비스 포트 |

결과: 정상 다운로드가 "위험"으로 표시되지 않았고, 사용량 급증은 통계적으로 탐지됐습니다.

## 3. 테스트로 발견해 고친 문제

실제 데이터로 실험하면서 찾아낸 문제와 수정 내용입니다. 모두 회귀 테스트를 추가했습니다.

| # | 발견 상황 | 원인 | 수정 |
|---|---|---|---|
| 1 | 실제 캡처에서 "DNS 실패 위험"이 오탐됨 | 브라우저가 같은 도메인에 A·AAAA를 동시에 질의하는데, 이 네트워크의 DNS 서버는 AAAA에 응답하지 않음. A 질의는 성공해서 실제로는 문제가 없었음 | 같은 도메인의 다른 질의가 성공한 무응답은 '부분 무응답'으로 따로 집계하고 실패에서 뺌 |
| 2 | 루프백에서 정상 TCP 연결 40개가 "반복 연결 시도"로 경고됨 | 반복 연결 규칙이 연결 성공 여부를 보지 않았음 | 대상별 핸드셰이크 완료율이 50% 이상이면 정상 사용(폴링 등)으로 판정 |
| 3 | 실제 다운로드가 "과다 패킷 위험"으로 표시됨 | TCP 수신 측은 지연 ACK와 수신 병합 때문에 데이터 약 5개당 ACK 1개(실측 0.19)만 보내는데, 양방향 판정 기준이 0.2였음 | 기준을 5%로 낮춤(일방적 폭주는 응답이 거의 0). 내 컴퓨터의 양방향 전송과 양방향 대용량 상대는 '정보' |
| 4 | 실제 다운로드 중 트래픽 급증이 탐지되지 않음 | 초당 6,700개 처리 시 처리가 실제 시각보다 몇 초 늦어지는데, 급증 규칙은 "현재 시각 기준 최근 5초"를 봐서 아직 처리하지 않은 빈 구간을 평가함 | 탐지 평가를 "처리한 패킷의 시각" 기준으로 1초마다 수행(pcap 분석과 같은 방식). 패킷이 없을 때만 실제 시각으로 평가 |
| 5 | SYN Flood 시나리오를 SYN-ACK 기준으로 판정하면 놓침 | 피해자 서버는 SYN-ACK를 보내므로 "응답률"이 높게 나옴 | 연결을 시작한 쪽의 마지막 ACK까지 추적해 3-way handshake 완료율로 판정 |
| 6 | UI에서 캡처 모달이 열리지 않음 (E2E로 발견) | 대시보드 API의 상태 객체에 `config` 필드가 빠져 JS 예외 발생 | 상태 응답을 하나의 함수로 통일 |
| 7 | 차단을 되돌려도 징후가 '조치 완료'로 남음 (E2E로 발견) | 롤백 시 징후 상태를 갱신하지 않음 | 롤백하면 징후를 다시 '확인 필요'로 되돌림 |
| 8 | 문서용 예제 IP(203.0.113.x)가 "같은 네트워크 장치"로 표시됨 | Python `ipaddress.is_private`이 문서용 대역도 사설로 봄 | RFC 1918 등 실제 사설망 대역 목록으로 직접 판정 |

### 방화벽 실제 차단·되돌리기 검증 (2026-11-22, Linux iptables · root)
NetCare API(`/api/actions/execute` → `/verify` → `/rollback`)로 문서용 예제 주소 203.0.113.50을 실제로 차단했다.
| 단계 | 결과 |
|---|---|
| 동의 없이 실행 | 거부 (`confirmation_required`) |
| 게이트웨이(192.0.2.1) 차단 시도 | 거부 (`protected`) |
| 동의 후 차단 | iptables에 `NetCare` 주석 규칙 2개 생성 (INPUT -s, OUTPUT -d) |
| 차단 효과 | 차단 전 즉시 연결 → 차단 후 연결 실패, DROP 규칙 카운터 2패킷 |
| 효과 검증(eth0 캡처 중) | "차단 후 이 IP로 나가는 데이터가 0개예요" (`traffic_verified: true`) |
| 되돌리기 | 규칙 제거, 다시 즉시 연결 |

### 방화벽 실제 차단·되돌리기 검증 (2026-11-22, Windows 11 netsh · 관리자)
`scripts/win_fw_verify.py`(임시 데이터 폴더 사용)로 같은 API 흐름을 실행했다. 로그: `docs/win_fw_verify_log.txt`
| 단계 | 결과 |
|---|---|
| 캡처 대조 | 기본 인터페이스 `이더넷`(192.168.100.110)에서 캡처, 차단 전 접속 시도 패킷 4개가 캡처에 잡힘 |
| 동의 없이 실행 | 거부 (`confirmation_required`) |
| 루프백(127.0.0.1) 차단 시도 | 거부 (`protected`, 내 컴퓨터 주소) |
| 동의 후 차단 | Windows 방화벽 규칙 `NetCare-Block-203.0.113.50` 2개 생성 (들어오는·나가는 방향, 작업: 차단) |
| 차단 효과 | 차단 전 1.5초 시간 초과(응답 없는 주소) → 차단 후 즉시 WSAEACCES 10013(방화벽이 막음) |
| 효과 검증(이더넷 캡처 중) | 차단 후 이 IP로 나간 패킷 0개 (`traffic_verified: true`) |
| 되돌리기 | 규칙 제거, 다시 1.5초 시간 초과(차단 전과 동일) |

이 검증 중 Windows 전용 버그 2개를 찾아 고쳤다.
- **명령 출력 인코딩:** 이 PC에서 `netsh`·`ping`·`ipconfig` 출력이 UTF-8로 나와 CP949로 읽다가 실패 → 조치 실행 자체가 오류. `decode_output()`으로 UTF-8 → 시스템 인코딩 → CP949 순으로 읽도록 수정.
- **기본 인터페이스 인식:** Scapy 장치 이름과 Windows 어댑터 이름이 달라 모든 인터페이스가 기본 아님으로 표시 → 루프백이 목록 맨 위. 기본 경로의 출발 IP로 찾도록 수정.

macOS pf 백엔드는 실제 실행하지 않았다(명령 생성·문법 검사만).

## 4. 한계와 검증하지 못한 항목

**검증하지 못한 항목 (구현은 했으나 실제 실행으로 확인하지 못함)**
- **macOS pf 실제 차단과 해제:** 관리자 권한이 없는 환경이라 실제로 실행하지 못했습니다. 확인한 범위는 규칙 파일 문법 검사(`pfctl -n`, root 불필요 → 통과), 명령 생성, 출력 파싱/롤백 토큰 단위 테스트, 테스트 데이터 기반 시뮬레이션·롤백 흐름(UI E2E)입니다.
  → 직접 검증 방법: `sudo .venv/bin/python run.py`로 실행한 뒤, 본인이 관리하는 기기 IP를 대상으로 차단 → 해당 IP에 `ping` 실패 확인 → "효과 검증" → "되돌리기" → `ping` 성공 확인.
- **DNS 캐시 초기화(macOS):** 관리자 권한이 필요해서 실행하지 않았습니다(권한 안내 흐름만 확인).
- **자동 차단(옵트인):** 관리자 권한으로 실행할 때만 동작하도록 해 두었고, 실제 동작은 확인하지 못했습니다. 동의 없이 켤 수 없다는 점은 테스트했습니다.

**구조적 한계**
- Python과 Scapy의 처리 속도: 초당 수천 패킷 수준에서는 버린 패킷 없이 처리했지만, 그 이상에서는 처리 지연과 누락이 생길 수 있습니다. 누락 수는 화면에 표시합니다.
- 캡처는 방화벽보다 먼저 일어나므로, 차단한 IP에서 **들어오는** 패킷도 캡처에는 보입니다. 그래서 차단 검증은 "내가 보내는 패킷이 0인지"로 판정하고 화면에도 그렇게 설명합니다.
- 통계 기준선은 프로그램이 지켜본 시간만으로 학습합니다. 관찰 시간이 짧으면 평범한 다운로드도 '급증'으로 보일 수 있습니다(최대 '주의' 등급).
- 출발지를 위조한 공격, 암호화 트래픽의 내용 기반 탐지는 범위 밖입니다.
- 프로세스 확인: macOS에서 관리자 권한이 없으면 내 계정 프로세스만 보입니다.
- IP→도메인 표시는 이 컴퓨터가 관찰한 DNS 응답에 기반합니다. CDN처럼 IP 하나를 여러 도메인이 공유하면 마지막으로 관찰한 이름이 표시됩니다.
