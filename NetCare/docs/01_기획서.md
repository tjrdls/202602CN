# NetCare 1단계 기획서

> 초보자 친화형 실시간 네트워크 패킷 분석 및 자동 문제 해결 시스템
> Beginner-Friendly Real-Time Network Monitoring and Automated Troubleshooting System

---

## 1. 실현 가능성과 기술적 한계

| 항목 | 가능 여부 | 한계와 대응 |
|---|---|---|
| 실시간 패킷 수집 | 가능 (Scapy + OS 캡처 드라이버) | macOS는 `/dev/bpf*` 권한(access_bpf 그룹 또는 sudo), Linux는 root 또는 `CAP_NET_RAW`, Windows는 Npcap 설치와 관리자 권한이 필요합니다. 권한이 없으면 화면에 해결 방법을 띄웁니다. |
| 헤더 분석 (Ethernet/IP/TCP/UDP/ICMP/IPv6) | 가능 | Scapy 디섹터로 계층별로 분해합니다. **HTTPS 본문은 암호화돼 있어 볼 수 없습니다.** TLS 레코드 헤더와 ClientHello의 SNI(평문으로 전송되는 접속 도메인)만 표시하고, 나머지는 "암호화된 데이터"라고 명시합니다. |
| 처리 성능 | 초당 수천 패킷 수준 | Python과 Scapy의 한계로 초당 수만 패킷 이상에서는 누락이 생길 수 있습니다. 큐가 가득 차면 버린 패킷 수를 세어 화면에 그대로 보여 주고, 통계가 그만큼 부정확할 수 있다고 안내합니다. |
| 이상 탐지 | 가능 (규칙 + 통계) | 패킷 수만으로는 공격 여부를 확정할 수 없습니다. "이상 징후"라고만 표현하고, 오탐 가능성과 그 근거(양방향 통신 여부, 연결 성공률, 잘 알려진 서비스인지 등)를 함께 보여 줍니다. |
| 자동 해결 | 일부 가능 | 실제로 실행하고 검증할 수 있는 조치만 넣었습니다. 연결/지연/DNS 진단, DNS 캐시 초기화, 의심 IP 방화벽 차단/해제(롤백), 통신 중인 프로세스 확인입니다. 공유기 설정 변경처럼 검증할 수 없는 조치는 안내만 합니다. |
| 프로세스 식별 | 부분 가능 | macOS에서는 관리자 권한이 없으면 내 계정 프로세스만 보입니다(`lsof`). 그 범위를 명시합니다. |
| AI 설명 | 선택 사항 | 기본 진단과 설명은 모두 **규칙 기반으로 AI 없이** 동작합니다. AI 연동은 확장 포인트로만 남겼고, 키는 환경변수로만 받습니다. |

## 2. 기술 스택과 선택 이유

| 분야 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.10+ | 요구사항이고, Scapy 생태계를 쓸 수 있습니다. |
| 캡처/분석 | **Scapy** (libpcap/BPF/Npcap 위에서 동작) | 계층별 디섹션, BPF 필터, pcap 읽기를 모두 지원합니다. |
| 데이터 처리 | Pandas | CSV 내보내기와 리포트 집계에 씁니다. |
| 저장 | **SQLite (WAL 모드)** | 설치가 필요 없고, WAL 모드라 쓰는 도중에도 동시에 읽을 수 있습니다. |
| 그래프 | **Plotly.js** (Python plotly 패키지에 들어 있는 파일을 로컬에서 제공) | 인터넷/CDN 없이 동작하고 실시간으로 갱신할 수 있습니다. |
| 백엔드 | **FastAPI + Uvicorn** | 비동기 API이고, 캡처 스레드와 웹 서버가 분리됩니다. |
| 프런트엔드 | **HTML + CSS + Vanilla JS (빌드 없음)** | 아래 비교 참고 |
| 이상 탐지 | 규칙 기반 임계값 + EWMA 기반 z-score | 처음에는 임계값을 설정해서 쓰고, 기준선이 학습되면 통계 탐지를 함께 적용합니다. |
| 자동 조치 | macOS `pfctl` / Linux `iptables` / Windows `netsh` | OS 기본 방화벽을 쓰고, 변경 전 상태 기록과 롤백을 지원합니다. |
| PDF | ReportLab | 한글 폰트를 넣은 실제 PDF 파일을 만듭니다. |

### Streamlit vs React vs FastAPI + 정적 프런트엔드

| | Streamlit | React + Python | **FastAPI + Vanilla JS (채택)** |
|---|---|---|---|
| 토스 스타일 UI | CSS 주입 정도만 가능. 카드/드로어/모달/애니메이션에 한계 | 자유도가 가장 높음 | 자유도 높음 (직접 만든 CSS) |
| 실시간 갱신 | 매번 스크립트 전체를 다시 실행. 캡처 스레드와 상태를 공유하기 어려움 | WebSocket/폴링 | 1초 폴링, 바뀐 부분만 다시 그림 |
| 백그라운드 스레드 | 세션 수명과 얽혀 불안정 | 서버에서 분리 | 서버 프로세스 하나에 캡처 스레드를 따로 둠 |
| 설치/실행 | 쉬움 | Node.js 빌드 체인 필요 | **`pip install`과 `python run.py`만으로 끝** |
| 초보 팀원 유지보수 | 쉬움 | 어려움(JSX, 번들러) | 보통 (HTML/CSS/JS 기본기면 충분) |

**결론:** Streamlit으로는 토스 수준의 UI와 안정적인 백그라운드 캡처를 함께 맞추기 어렵습니다. React는 빌드 체인 부담이 큽니다. 그래서 FastAPI 백엔드와 빌드가 필요 없는 정적 SPA를 채택했습니다.

│                                                                                          │
│  [Remediation] 조치 카탈로그 → 미리보기 → 사용자 승인 → 실행 → 검증 → 롤백 (actions 테이블)│

**스레드 분리 원칙:** 캡처 콜백은 패킷을 큐에 넣기만 합니다. 파싱, 통계, 탐지, DB 쓰기는 처리 스레드가 배치 단위로 맡습니다. 웹 요청은 공유 상태를 잠금(lock) 아래에서 스냅샷으로만 읽기 때문에 UI가 캡처를 막지 않고, 캡처도 UI를 막지 않습니다.

## 5. 기능별 구현 방법

### 기능 1. 실시간 패킷 수집
- `scapy.AsyncSniffer(iface, filter, prn, store=False)`로 패킷을 수집하고 콜백에서는 `queue.put_nowait`만 합니다.
- BPF 캡처 필터는 시작 전에 `compile_filter`로 문법을 검사하고, 틀리면 친절한 오류를 돌려줍니다.
- 인터페이스 목록에는 IP, MAC, 하드웨어 이름(Wi-Fi, USB LAN 등)을 붙이고, 기본 경로 인터페이스를 추천합니다.
- 캡처한 시간(`pkt.time`), 와이어상 크기(`len(pkt)`), 출발지/목적지를 기록합니다.
- 업로드/다운로드 방향은 인터페이스의 MAC과 로컬 IP를 비교해 판정합니다.

### 기능 2. 헤더 분석
- 요약 레코드: MAC, EtherType, IP 버전, TTL/Hop Limit, 프로토콜, 길이, 포트, SEQ/ACK, 플래그, 윈도우, UDP 길이, ICMP 타입, DNS 질의/응답 코드, TLS SNI.
- 상세 보기: DB에 저장한 원본 바이트를 Scapy로 다시 해석해 계층 트리를 만듭니다. 필드마다 기술명, 한국어 이름, 값, 설명이 붙습니다. 헥사 덤프도 함께 보여 줍니다.

### 기능 3. 통계
- 초 단위 버킷(최근 1시간)과 누적 카운터(Counter)를 씁니다. PPS는 직전 5초 평균입니다.
- 프로토콜 비율, 출발지/목적지 IP Top-N, 포트(서비스)별 패킷과 바이트, 평균/최대 크기, 총 전송량을 모두 실제 캡처한 레코드로만 계산합니다.

### 기능 4. 시각화
- Plotly.js로 시간별 PPS, 실시간 사용량(bps), 업/다운로드, 프로토콜 도넛, IP/포트 막대 그래프를 그리고 1초마다 `Plotly.react`로 갱신합니다.

### 기능 5. 이상 탐지
| 규칙 | 기준 (기본값, 설정 가능) | 오탐 완화 |
|---|---|---|
| ① 특정 IP 과다 패킷 | 10초 평균 PPS ≥ 300 | 상대가 응답하는 양방향 통신(역방향 5% 이상, TCP 지연 ACK 고려)이면 한 단계 낮춤. 내 컴퓨터의 양방향 전송은 '정보' |
| ② SYN 급증 | 10초에 순수 SYN ≥ 60 **그리고** 3-way handshake 완료율 < 30% | SYN-ACK이 아니라 연결을 시작한 쪽의 마지막 ACK까지 확인. 완료율이 높으면 정상 연결 폭주로 보고 알리지 않음. 출발지를 여러 개로 나눈 분산 SYN도 탐지 |
| ③ 포트 집중 | 한 포트가 전체의 80% 이상 **그리고** 10초에 2,000패킷 이상 | 443/80/53 같은 일반 서비스는 '정보' 등급 |
| ④ 트래픽 급증 | 기준선 학습 후 EWMA z-score ≥ 4 **그리고** ≥ 1MB/s, 학습 전에는 고정값 10MB/s | 60초 워밍업, 이상 구간은 기준선 학습에서 뺌, 위협이 아닌 사용 패턴 신호라서 최대 '주의' |
| ⑤-a 반복 연결 | 같은 목적지:포트로 10초에 SYN ≥ 30 **그리고** 연결 완료율 < 50% | 정상적으로 완료되는 폴링/API 호출은 제외. RST 응답(상대가 거부)은 원인 설명에 반영 |
| ⑤-b 포트 스캔 패턴 | 한 IP가 10초에 서로 다른 목적지:포트 ≥ 40곳에 연결 시도 | — |
| ⑤-c 특정 IP 과다 통신 | 한 IP가 전체 바이트의 90% 이상 **그리고** ≥ 2MB/s | 양방향이면 '정보'. 대개 대용량 다운로드 |
| DNS 실패 | 10초에 오류 응답 또는 무응답 ≥ 5건, 비율 ≥ 50% | 같은 도메인의 다른 질의(A/AAAA 중 하나)가 성공한 무응답은 실패에서 뺌 |
| 연결 품질 (Prober) | 게이트웨이 손실 ≥ 50%, 지연 ≥ 200ms 등 | 실측 ping 결과 |

- 위험 수준은 측정값/기준값 비율로 정합니다(1배 이상 '주의', 3배 이상 '위험'). 화이트리스트에 있는 IP는 탐지하지 않습니다.
- 탐지 평가는 '처리한 패킷의 시각'을 기준으로 1초마다 합니다. 패킷이 몰려 처리가 늦어져도 평가 창이 아직 처리하지 않은 빈 구간을 보지 않게 하기 위해서입니다. 이 문제는 실제 네트워크 실험에서 발견했습니다.
- 같은 종류의 징후가 같은 대상에서 60초 안에 다시 나오면 새 알림을 만들지 않고 기존 건을 갱신합니다(횟수, 최고값). 이렇게 해서 알림 폭주를 막습니다.

### 기능 6. 진단과 해결 → 7절

## 6. UI/UX 설계안 (토스 스타일)
- **색상:** 배경 `#F2F4F6`, 카드 `#FFFFFF`, 주색 초록 `#00B26B`, 주의 `#FF8A00`, 위험 `#F04452`, 본문 `#191F28`, 보조 `#8B95A1`.
- **타이포그래피:** 시스템 한글 폰트(Apple SD Gothic Neo / Malgun Gothic / Pretendard 사용 가능 시). 큰 숫자 28~40px, 굵기 700.
- **레이아웃:** 상단 바(로고, 인터페이스 선택, 시작/중지, 전문가 모드, 설정) 아래에 4개 탭을 둡니다. 화면이 좁으면 하단 탭 바로 바꿉니다(반응형).
- **홈:** 상태 링(점수, "안정적이에요"/"확인이 필요해요"/"문제가 있어요"), "왜 이 점수인가요?" 펼치기, KPI 카드 5개, 실시간 그래프, 최근 활동 문장, 통계 카드.
- **패킷:** 필터 칩(전체/TCP/UDP/ICMP/DNS/웹), 검색, 일시정지, 쉬운 문장으로 쓴 패킷 행. 행을 누르면 오른쪽 드로어에 "쉬운 설명" 카드와 계층 트리(아코디언)가 열리고, 전문가 모드에서는 헥사 덤프도 보입니다.
- **문제 해결:** 위험도 색 띠가 붙은 카드 목록을 두고, 상세 화면은 "무슨 일인가요 → 왜 그렇게 판단했나요(기준 대비 측정값 게이지) → 어떤 영향이 있나요 → 오탐일 수도 있어요 → 이렇게 해결해 보세요" 순서로 구성합니다. 조치 버튼을 누르면 확인 모달(할 일, 부작용, 실행 명령, 관리자 권한, "이해했어요" 체크)이 뜨고, 실행 → 결과 → 검증 → 되돌리기 순으로 진행합니다.
- **리포트:** 기간(오늘/7일/30일), 일별 사용량, 프로토콜, IP, 포트, 건강 점수 추이, 이상 이력, CSV/PDF 내보내기.
- **데이터 출처 배지:** 실시간 캡처 / pcap 파일 / 테스트 데이터를 항상 표시하고, 리포트에서는 기본으로 테스트 데이터를 뺍니다.

## 7. 자동 진단 및 해결 기능 구현 방법
1. **원인 분석:** 탐지 결과의 증거(측정값, 방향, 상대 응답, 프로토콜, 도메인)를 써서 "무엇/누가/어떤 프로토콜/왜/영향"을 채웁니다.
2. **자연어 설명:** 규칙마다 템플릿이 있고, 관련 장치를 "내 컴퓨터 / 같은 네트워크의 장치 / 외부 인터넷(도메인)"으로 바꿔 말합니다.
3. **추천:** 문제 유형별로 실제 관련된 조치만 연결합니다. 예를 들어 DNS 실패에는 DNS 조회 테스트와 캐시 초기화를, 의심 IP에는 통신 내역 확인, 프로세스 확인, 차단 검토를 연결합니다.
4. **조치 카탈로그:** 조치마다 `requires_admin`, `changes_system`, `reversible`, `side_effects`, 미리보기 명령이 붙어 있습니다.
5. **승인:** 시스템을 바꾸는 조치는 API에서 `confirm=true`와 `acknowledge_risk=true`가 모두 있어야 실행합니다. UI에서는 체크박스를 눌러야 버튼이 켜집니다.
6. **안전장치:**
   - 자동 차단은 기본으로 꺼져 있습니다. 켜려면 설정에서 경고를 읽고 동의해야 하고, 켜도 외부 공인 IP의 '위험' 등급 SYN 급증, 포트 스캔, 단방향 폭주에만 적용합니다. 30분이 지나면 자동으로 해제됩니다.
   - 보호 IP(내 IP, 게이트웨이, DNS 서버, 루프백, 멀티캐스트/브로드캐스트, 화이트리스트)는 차단을 거부합니다.
   - 사설망 장치를 차단할 때는 "같은 네트워크 장치와의 통신이 끊길 수 있다"고 따로 경고합니다.
   - 실행 전 상태(pf 활성 여부, 테이블 내용, iptables-save 등)를 기록하고 롤백 정보를 저장합니다.
   - 관리자 권한이 없으면 실행하지 않고 직접 실행할 명령을 안내합니다. macOS에서는 사용자가 원하면 OS 관리자 암호 창으로 실행할 수 있습니다.
   - 테스트 데이터에서 나온 징후로는 실제 방화벽을 바꾸지 않고 시뮬레이션(명령 미리보기)만 합니다.
7. **검증:** 차단 후에는 방화벽 규칙이 들어갔는지 확인하고, 이후 해당 IP의 수신 패킷이 0인지 봅니다. DNS 초기화 후에는 조회를 다시 테스트하고, 진단 결과는 실측값으로 판정합니다.
8. **롤백:** 차단 해제(규칙 삭제), 그리고 pf를 NetCare가 켰다면 토큰을 반납해 원래 상태로 돌립니다.

## 9. 예상 문제점과 해결 방안
| 문제 | 해결 |
|---|---|
| 캡처 권한 부족 | 권한 오류를 잡아 OS별 해결법(sudo, access_bpf 그룹, Npcap, setcap)을 안내합니다. pcap 파일 분석과 테스트 데이터 모드는 권한 없이도 됩니다. |
| 패킷 폭주로 UI가 멈춤 | 제한 큐와 배치 처리를 쓰고, UI는 링버퍼와 요약만 폴링합니다. 넘친 패킷은 버리고 그 수를 표시합니다. |
| DB가 커짐 | 패킷 보존 한도(기본 30만 개)를 넘으면 오래된 것부터 지웁니다. 분 단위 집계는 따로 남겨서 리포트에 씁니다. |
| 오탐 | 양방향/성공률/서비스 포트 휴리스틱을 쓰고, 워밍업 기간을 두고, 화이트리스트와 "정상이에요" 피드백을 받습니다. 표현은 "징후"로만 합니다. |
| OS별 명령 차이 | 방화벽 백엔드를 추상화(pf/iptables/netsh)하고, 지원하지 않는 OS에서는 안내만 합니다. |
| 로컬 API 악용 (CSRF, DNS 리바인딩) | 127.0.0.1에만 바인딩하고, Host 헤더를 검사하고, 변경 요청에는 커스텀 헤더를 요구합니다(교차 출처 preflight 차단). |
| HTTPS 내용 오해 | 암호화 영역은 "복호화 없이 볼 수 없음"이라고 명시하고, SNI 같은 평문 메타데이터만 보여 줍니다. |
